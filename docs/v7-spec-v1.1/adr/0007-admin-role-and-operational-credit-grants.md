# ADR-0007：管理员角色与运营赠点账务

- 状态：Accepted
- 日期：2026-07-20
- 关联：PRD §1.4、§2.7、§2.8，Development Plan P8.3

## 背景

V7 管理后台需要执行租户停用与运营赠点。两类操作都会改变平台安全边界或可消费余额，不能只依赖前端入口隐藏，也不能直接覆盖账户余额。系统还必须处理重复提交、已有会话在租户停用后的失效，以及一次操作在订单、账本和审计之间的一致性。

## 决策

1. `users.is_admin` 是当前阶段的服务器端平台管理员标记。每个管理 API 都从当前会话重新加载用户并校验该标记；Creator 会话即使能够访问同域 Cookie，也不能绕过服务端角色校验。
2. 每次会话校验同时读取租户状态。租户被停用后，已有会话立即失效，而不是等待 JWT 或 Cookie 自然过期。
3. 管理员不能从当前会话停用自己所属的租户，避免单管理员开发环境被误锁；其他租户的停用和恢复均要求 CSRF 并写入 append-only 审计日志。
4. 运营赠点在一个数据库事务内完成三项写入：创建 `orders(kind=grant)`、向 `credit_ledger` 追加 `operation=grant` 记录、增加 `token_accounts.credits_remaining`。任何一步失败都整体回滚。
5. `credit_ledger.reservation_id` 只对运行消费链必填；订单赠点等非运行账务允许为空，并以唯一 `reference_key` 关联业务幂等键。账本仍保持 append-only，不允许更新历史余额记录。
6. 客户端为每次赠点生成 `idempotency_key`。相同键与相同载荷返回原结果且不重复入账；相同键但载荷不同返回冲突。
7. 订单、账本与审计保存操作者、租户、等级作用域、前后余额及备注。后台只显示操作结果，不把前端状态作为账务事实源。
8. 管理员创建租户时，在一个事务内创建租户、所有者与首个等级额度账户；所有者邮箱全局唯一，临时密码只保存 Argon2 哈希。等级变更保留旧等级的独立点数账户，并按新等级创建或恢复其额度账户，避免跨等级挪用点数。
9. 租户创建、状态变更、等级变更和赠点分别记录 `tenant.create`、`tenant.status.change`、`tenant.tier.change` 与 `tenant.credits.grant` 审计动作；“改余额”不作为通用管理操作开放。

## 后果

- 后台写操作具备可追溯、可重放且不重复记账的最小闭环。
- 租户停用会立即阻断已有 Creator/Admin 会话，减少撤权窗口。
- 当前角色模型适合 V7 单管理员阶段；独立管理端 audience、细粒度 RBAC 与双人审批留待 P9 安全硬化，不宣称已经完成。
- 后续购买、退款和等级变更应复用订单与 append-only 账本原则，但分别定义状态机，不能把 `grant` 伪装成通用余额修改。
