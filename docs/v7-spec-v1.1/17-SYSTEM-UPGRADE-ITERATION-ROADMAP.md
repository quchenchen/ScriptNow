## 1. 执行摘要

ScriptNow 已经从“原型拼接”进入了“真实模型、真实数据、真实候选与人工采纳能够局部闭环”
的阶段，但还没有达到生产级创作系统要求的**可恢复、可解释、可度量和四领域一致可靠**。

当前最大的风险不是功能数量不足，而是同一次创作在页面、Dock、AgentScope run 和领域产物
之间仍可能存在四套不同的状态。只要这一层没有收敛，继续增加模型、Skill、图谱、包装或
Dreaming 都会放大等待、重复生成、状态错乱和错误学习。

下一轮升级遵循以下顺序：

1. 建立统一且耐久的 operation、stage、artifact、decision 与 checkpoint；
2. 让 AgentScope 真实事件、创作搭档和页面操作共享同一运行事实；
3. 分别完成 Novel、Script、忠实翻译和故事归化的领域流水线；
4. 再建设质量锚点、Skill 评测、项目记忆和受控 Dreaming；
5. 最后完成全量体验治理、发布加固和无界面接口评审。

CLI 与外部 Agent 接入继续保留为备选计划，不进入本轮主线。先让 Web 和公开应用接口变得
可靠，避免把现有问题复制到第二套入口。

成本路由不属于本轮交付范围。当前只保留既有用量记账与运行快照，不新增按价格自动选模、
按阶段降档或基于预算改写创作策略的逻辑；重新启动必须由新的产品决策和独立 ADR 批准。

## 2. 审计依据

本次结论来自四类证据，而不是只依据待办清单：

1. v1.1 唯一规格基线及现有实施计划；
2. 当前代码、数据库迁移、前后端测试和构建配置；
3. 2026-07-28 在本地运行环境对项目控制台、Script 创作现场、创作搭档、作品包装和管理端
   的实际检查；
4. `13-CREATIVE-FLOW-TECHNICAL-AUDIT.md` 中记录的真实运行耗时、失败率和重复故障。

本次页面证据保存在：

```text
.artifacts/audits/2026-07-28-system-upgrade/
```

证据中可直接观察到：

- Script 场次候选已经具备“生成候选 → 只读 → 明确确认”的基本边界；
- Dock 已有真实项目事件、Agent 回复、模型和上下文占用信息；
- 同一场次在正文候选和 Dock 后续回复中仍可能出现两个未关联版本；
- Dock 当前上下文已达到 `26,830 / 32,768`，但项目长期记忆仍为 0；
- Dock 将完整创意方向和长篇回复直接铺陈，信息密度过高，内部事件分类仍主导交互；
- Script 项目包装仍使用“书名、约 200 词简介、Wattpad/Webnovel”语义，说明跨领域运营层
  尚未完成独立契约；
- 管理端显示租户“正常”但额度已耗尽、点数为负，开发期策略和状态语义不一致；
- 项目控制台能进入各类项目，但缺少统一的阶段、阻塞、待决定和最近产物摘要。

## 5. 系统性断点

### P0：不修复就不能称为可靠创作系统

#### 5.1 成功状态没有统一以可消费产物为边界

模型返回、run 完成、事件结束和领域候选落盘目前不是同一个原子完成边界。Script 已修复
部分 StoryMap 场景，但 Novel、Translation、Recreation 尚未完成同等级审计。

**不变式：**

```text
operation succeeded
  ⇔ domain validation passed
  ∧ artifact persisted
  ∧ artifact can be read by the next stage
  ∧ user projection published
```

缺少任一项都只能是 `failed`、`waiting` 或 `partial`，不得通过兜底文本伪装成功。

#### 5.2 统一耐久内核已建立，但恢复闭环尚未完成

当前已建立统一的 `CreativeOperation → StageRun → Artifact → Checkpoint → Decision`
持久化谱系，并接入四领域主要生成入口。Context Manifest、恢复判定矩阵、parked
AgentState 序列化及一次性 resumption claim 已有自动化证据。剩余风险是将 AgentScope
`RequireUserConfirmEvent` 接入真实 MCP 调用并完成进程重启后的端到端续跑；在该验证通过前，
不得宣称工具副作用具备 exactly-once。

#### 5.3 确认仍未完整对应 AgentScope 的暂停与恢复

页面中的“确认”与 AgentScope 的 `RequireUserConfirmEvent`、parked `AgentState` 和
`UserConfirmResultEvent` 尚未形成持久、幂等、恰好一次的完整链路。确认前后的工具副作用和
领域采纳必须共享同一 operation 与幂等键。

#### 5.4 Dock 补造事件已止血，真实桥仍需完善

`DockService.send_message()` 已停止在 `runtime.generate()` 返回后补造 thinking/tool
fixtures；当前只投影真实项目上下文 DataBlock、Agent TextBlock 与终止事件。下一步仍需把
AgentScope 原生确认、工具事件和 parked AgentState 接入同一持久化桥，禁止重新引入展示性
伪事件。

#### 5.5 Dock 回复与领域产物没有强制血缘

当前页面可见的场次候选和 Dock 内后续“重写稿”可能同时存在，但用户无法从一个对象跳转到
另一个对象，也无法判断哪个进入下一场上下文。所有长文本回复必须是：

- 纯消息；或
- 明确关联到 `ArtifactRef` 的候选；或
- 对既有 artifact 的修订提议。

禁止存在“看起来像成品、实际上没有版本身份”的第三种文本。

### P1：决定系统能否高质量、流畅地扩展

#### 5.6 四领域只有目录隔离，尚未完成体验与运营隔离

Script 包装页仍展示网文平台规格和“约 200 词简介”，说明共享组件越过了领域边界。四领域
可以共享运行、账本、认证、Provider 和文件安全，但不能共享作品格式、质量规则、包装字段
和导出策略。

#### 5.7 长上下文替代了项目记忆和最小上下文

当前 Dock 实例已使用 82% 上下文，但长期记忆为 0。继续整包注入蓝图、StoryMap、历史消息
和正文会造成成本、遗忘、响应慢和输出漂移。需要 `ContextManifest` 明确说明本次使用了
哪些事实、版本、摘要、Skill 和原文证据。

#### 5.8 信息架构仍服务于内部事件，不服务于作者任务

“重点 / 对话 / 确认 / 过程 / 运行”混合了投影、消息、决策和诊断。作者真正需要的是：

1. 本轮目标与计划摘要；
2. 当前正在做什么；
3. 哪个产物已经形成；
4. 现在需要决定什么；
5. 出错后如何继续。

运行 trace、模型 token 和工具原始事件默认折叠，仅在诊断权限下展开。

#### 5.9 质量和 Skill 尚未形成量化复利

题材模板、质量锚点和 SkillPlan 已有设计，但还不能回答：

- 本次实际采用了哪些 Skill；
- 与基线相比是否减少人工修改；
- 哪类题材、语言和阶段有效；
- 哪个 Skill 导致连续性或格式回归；
- 如何灰度、回滚和淘汰。

受控 Dreaming 只能在这些证据完整后启动，否则会把失败候选和历史噪音固化。

#### 5.10 性能和成本仍按整次 run 观察

历史数据中多个核心流程平均需要数分钟，图谱流程可超过十分钟。系统需要按 stage 记录
首状态、首个可读内容、校验、修复、持久化、总时长、token、缓存和有效 artifact 成本。

### P2：发布与长期维护债务

#### 5.11 缺少真实四领域 E2E 和故障恢复矩阵

当前自动化测试以 public interface 为主是正确的，但尚需补充真实 Provider 合约测试和以下
黄金路径：

- Novel 原创与改编；
- Script 原创与改编；
- 忠实翻译的术语纠偏、历史和导出；
- 故事归化的分析、策略、试写、逐包生产和导出；
- 刷新、断线、取消、Provider 超时和服务重启；
- 人工修订被下一章或下一场正确继承。

#### 5.12 前端没有路由级拆包

Creator 路由仍静态导入所有主要页面。作品图谱、编辑器、归化和包装继续增长时，会影响首屏
和开发反馈速度。需要按领域与页面懒加载，并把大型可视化依赖隔离为异步 chunk。

#### 5.13 国际化仍混合词条和源文替换

核心页面已有共享 locale，但仍存在直接中文文案和 `sourceMessages` 兼容映射。最终应统一为
稳定 key、参数化文案和按领域分包；用户内容、模型输出和界面文案必须保持三种不同语言语义。

#### 5.14 管理端状态语义没有闭环

当前可观察到“租户正常、额度耗尽、点数为负”同时存在。开发期可以放宽预算，但必须由环境
策略表达；不能让账本、可用性和 UI 状态互相矛盾。

## 6. 升级实施路线

### 阶段 0：冻结基线与建立黄金项目

**目标：** 停止以零散问题驱动主线，先建立可重复的证据。

- 固定 Novel、Script、Translation、Recreation 各一个脱敏黄金项目；
- 记录每一步输入、operation、stage、artifact、决定、版本和导出结果；
- 建立当前首状态、首字、总时长、token、失败类型和人工修改量基线；
- 建立跨领域完成定义和错误分类；
- 新需求只进入待评审池，不插入 P0 修复链。

**退出门：** 四个黄金项目可以一键重放，并能生成同格式审计报告。

当前已完成一致格式审计、真实领域物化和交付产物信封。四领域现有流程均可由同一执行器
审计，不再把契约测试等同于黄金路径通过。

2026-07-29 已使用四个现存项目执行真实 Provider 证据回放。四个项目均提供非 Mock 的
Provider、模型、运行快照和完整领域产物，并满足完整黄金场景：

- Novel：StoryMap 决策恰好一次，完整小说 DOCX 可交付；
- Script：StoryMap 决策恰好一次，场次、审读、包装与剧本 DOCX 可交付；
- 忠实翻译：完整译文 DOCX 可交付；
- 故事归化：审读、包装与归化作品 DOCX 可交付。

上述结果来自真实领域流程补齐缺失产物并重新通过同一审计器；没有删除阶段、补造运行事件
或把 `partial` 改写为成功。交付产物以版本、SHA-256 和字节数持久化，供后续回放复核。

平台真实运行故障闭环已先完成以下最小语义，作为阶段 1 的前置约束：

- Provider 超时稳定映射为 `agent_runtime_timeout` 和 HTTP 504，其他运行失败映射为
  `agent_runtime_failed` 和 HTTP 502，不再被二次状态迁移异常覆盖；
- 失败运行释放预留额度，并同时写入持久化终止事件与面向作者的系统事件；
- 服务启动时将无法跨进程存活的 `queued`、`running` 运行收敛为可重试的
  `runtime_interrupted`，保留已有持久化决定上下文的 `waiting` 运行；
- 当前阶段明确不宣称进程内 AgentScope 协程可在重启后继续。真正的续跑必须等待
  `Checkpoint` 与 `AgentState` 持久化完成，禁止用合成“恢复成功”事件替代。

### 阶段 1：创作运行真相与恢复内核

**目标：** 完成 `14-AGENTSCOPE-ALIGNED-IMPLEMENTATION-PLAN.md` 的 P0–P2。

- 新增持久化 CreativeOperation、StageRun、ArtifactRef、Checkpoint、DecisionRequest；
- API 在接受任务后快速返回 operation id，后台推进 stage；
- 四领域 success boundary 全部改为 artifact-backed；
- 把 active task registry 扩展到 Script、Translation、Recreation；
- 接入真实 AgentScope confirm、AgentState park/resume 和幂等副作用；
- 已删除 Dock 补造 thinking/tool fixtures，并把 Dock 消息、确认、取消接入最小
  Creative Session/Operation/StageRun/DecisionRequest 谱系；
- 实现刷新、断线、取消、重试和服务重启恢复。

**当前垂直切片：**

- Novel 章节生成已改为快速返回运行标识并由后台推进；
- Script 场次生成也已改为快速返回运行标识并由后台推进；
- Translation 单章翻译已改为快速返回运行标识，批量翻译按章节串行调用同一后台协议；
- 三个领域的同一次生成均可追溯到 CreativeSession、Operation、StageRun、ArtifactRef 与
  Checkpoint；
- 只有章节、场次候选或译文修订持久化并登记产物后，operation 与 run 才能进入成功状态；
- 同步调用仍保留兼容入口，但不再与后台运行重复创建或重复结束 run；
- Novel 与 Script 垂直切片均已通过后端、前端、lint 与双 SPA 构建全量门禁；
- Translation 已通过领域测试、后台谱系集成测试和仓库级门禁；
- Recreation 不得复制 Novel/Script/Translation 领域对象，只复用 platform 运行协议；
- Recreation “读懂原作”、三套归化策略候选、代表性试写、整书规划与逐章生产均已完成
  后台谱系垂直切片；所有生成结果只形成候选，不代替创作者审读、人工修订和明确采纳。
- Recreation 的审读、人工修订与采纳是独立、可审计的快速领域事务：人工修订生成新版本，
  修订后必须重新审读，最终采纳才改变正式作品事实。

**退出门：**

- 0 个无 artifact 的成功 operation；
- 0 个确认后重复采纳或重复副作用；
- 四领域运行重启后均能从最近 checkpoint 恢复；
- 用户不再看到 Pydantic、Provider 或内部 schema 原始异常。

### 阶段 2：统一创作搭档与页面操作

**目标：** 页面按钮和自然语言交互共用同一命令与事实。

- Dock 改为“本轮 / 对话 / 待决定 / 产物与进度”，诊断信息二级展开；
- 长内容必须落为 artifact，并显示版本、状态和打开/比较/采纳入口；
- 页面动作通过同一领域 command 发起，不再存在聊天旁路；
- 展示计划摘要，不展示隐藏思维链；
- 模型切换放在创作团队配置；运行中只显示本次冻结模型和切换影响；
- 上下文展示改为“已使用的项目事实与风险”，原始 token 仅在诊断层显示。

**退出门：** 从一句自然语言指令到形成候选、人工修订和采纳，不需要用户理解 run id、block
或内部事件类型，且页面与 Dock 始终指向同一个 artifact revision。

### 阶段 3：四领域独立生产流水线

按以下顺序完成，每个领域通过退出门后再进入下一个：

1. **Script**：场次调度、可见行动、可听台词、戏剧转折、格式策略、可拍性审读、剧本包装；
2. **Novel**：章节计划、正文流、连续性、题材与风格审读、后续章节继承人工修订；
3. **Translation**：有界章节并行、对照、术语状态机、纠偏影响分析、历史和独立导出；
4. **Recreation**：原作分析、策略、试写确认、整书工作包、逐包生产、文化与市场审读。

每个领域必须声明：

- 自己的 stage graph、artifact contract、context manifest；
- schema 归一化与定点修复；
- 质量门和人工决策边界；
- 包装、版本和导出契约；
- 允许复用的平台能力以及禁止跨域复用的领域能力。

**退出门：** 每个黄金项目连续运行三次，无状态错乱、无全量重做式修复、无跨领域字段。

### 阶段 4：质量锚点与 Skill 证据闭环

**目标：** 用质量提升证明 Skill，而不是用 Skill 数量证明能力。

- 为题材、结构、人物、情感、剧本可拍性、翻译忠实度和归化质量建立分层 benchmark；
- 每次 operation 固定 SkillPlan digest、上下文和模型快照；
- 记录采纳、拒绝、撤销、人工 edit delta、连续性缺陷和质量锚点变化；
- Skill 依次经过静态契约、历史回放、shadow、project canary 和发布；
- 低效或造成回归的 Skill 可自动降级为候选并一键回滚。

**退出门：** 任一 Skill 发布都能回答“比什么基线好、在哪类任务有效、成本是多少、如何回滚”。

### 阶段 5：速度、成本、图谱与项目记忆

- 实施 fast/deep 双通道和按任务能力路由，不硬编码模型名称；
- 使用最小 ContextManifest、变化集、摘要缓存和相关事实检索；
- 图谱改为增量提取、低成本候选、领域校验和按需可视化；
- 项目记忆只沉淀已确认事实、偏好和人工修订，不把未采纳候选写入长期上下文；
- 建立每个有效 artifact 的 token、时延、重试和人工修订成本。

**退出门：** 质量不下降的前提下，黄金项目 P50 总时长和每个已采纳产物 token 成本相对阶段
0 基线都有可复现下降。

### 阶段 6：受控 Dreaming、体验治理与发布加固

- 在完整 ExperienceEpisode 与负例账本上实现项目级 Dream 候选；
- 只允许项目记忆去重、矛盾、过期和 Overlay 建议先行；
- 完成全量 i18n key 迁移、主题对比度、响应式和键盘可访问性；
- Creator/Admin 路由级拆包并建立 bundle 预算；
- 补齐四领域 E2E、Provider 合约、恢复、软删除与备份恢复测试；
- 完成安全、租户隔离、账本冲正、审计和发布演练。

**退出门：** `make test && make lint && make build`、四领域黄金 E2E、重启恢复和安全检查全部
通过；发布后可从操作、产物和质量指标追溯任一问题。

## 7. 统一指标

指标目标由数据库策略和发布门管理，不写死在业务代码或测试 fixture 中。

### 正确性

- False success 数量；
- 无 artifact 的 completed operation 数量；
- 重复采纳、重复副作用和版本错链数量；
- 后续章节/场次未继承最新人工修订的数量。

### 流畅性

- 任务接受到首状态、首个可读内容、candidate ready 的耗时；
- 用户等待中无状态变化的最长间隔；
- 刷新、断线和重启后的恢复耗时；
- 完成一次任务所需页面跳转、重复输入和人工重试次数。

### 质量

- 采纳、拒绝、撤销率；
- 人工 edit distance；
- 连续性、结构、格式、术语和文化适配缺陷；
- 与质量锚点和人工盲评基线的差异。

### 成本

- 每个已采纳 artifact 的输入/输出 token；
- 定点修复率与全量重做率；
- 缓存命中率；
- 不同模型路由的质量、时延和成本曲线。

### 体验

- 黄金流程任务完成率；
- 错误后自主恢复率；
- 待决定事项处理时长；
- Dock 中被打开、忽略和造成重复操作的信息比例。

## 8. 研发治理

1. 同一故障在第二个领域出现时，立即升级为平台问题，不再复制局部补丁。
2. 每次黄金项目验证必须输出阶段瀑布、状态迁移、产物血缘和质量差异。
3. 所有用户可见成功必须有可打开的 artifact。
4. 所有业务参数来自项目契约、设置、数据库策略或 Agent 交互。
5. 不用 fallback 文案掩盖结构化输出、Block 解析、Provider 或领域校验错误。
6. 新增共享组件前必须列出共享的是平台语义还是领域语义。
7. 任何 Dream、Memory 或 Skill 晋升必须有正例、负例、回放、审批和回滚。
8. CLI、MCP/A2A 和外部 Agent 接入只有在阶段 1–3 通过后才重新评审。

## 9. 本轮建议范围

立即进入阶段 0 和阶段 1，不同时启动 Dreaming、CLI 或更多题材 UI 扩张。

首个研发包只包含：

1. 四领域 success-boundary 审计与 artifact-backed tests；
2. CreativeOperation/StageRun/ArtifactRef/DecisionRequest 最小迁移；
3. Script、Translation、Recreation active task registry；
4. 真实 AgentScope confirm/park/resume tracer bullet；
5. 删除 Dock 补造事件并建立真实 event bridge；
6. 当前四个黄金项目审计报告生成器。

这个研发包完成后，ScriptNow 才具备继续扩展创作能力而不继续积累双轨状态的基础。
