圆桌讨论：ScriptNow API 测试发现

参与者：API 工程师 · 交互体验设计师 · Agent 协作专家 · 系统架构师  |  2026-07-25

🔧 林工 — API 可靠性工程师

我先说最直接的。API 的健壮性是所有上层体验的底座。这次测试暴露了三个模式级问题：

1. 静默失败 — StoryMap 生成时 volume 参数为空，API 返回 200 但 volumes=[]。前端永远锁死在"等 StoryMap 就绪"。这是最差的一类 bug，因为没有任何错误信号。

2. 幽灵完成 — 6 次生成请求中 3 次客户端超时，但后台实际完成了。API 应该返回异步任务引用（run_id），而不是让客户端盲目猜测"它到底完了没"。

3. 字段类型不做自愈 — volume_one 传 1 报 422，传 "1" 才 200。这不是 Schema 校验的问题——direction 是自由 JSON，应该在入口做 normalize。

我的建议：强制所有异步操作用 run_id 模式，加 direction normalize。这两个修了，80% 的 API 健壮性问题就没了。

🎨 苏然 — 交互体验设计师

林的建议很好，但我要补充一个视角：人不是通过 API 和 Agent 交互的。API 修到完美，也不等于交互体验好。

4. Agent 生成过程中用户是完全盲的。2-3 分钟的等待时间里，前端连一个"正在构思第 2 章节奏节点…"的状态都没有。不是技术问题——run_stream_events 表里已经有事件数据，只是前端没消费。

5. 反馈闭环不存在。Writer 写完一章，Reviewer 给出质量报告——但报告永远不回到 Writer 手里。用户必须手动复制 Reviewer 的评语粘贴到 Writer 的 feedback 框。这违背了"Agent 协作"的核心理念。

6. 采纳操作无确认。点"采纳"后候选直接变成了已采纳，但没有任何视觉信号告知用户"采纳后发生了什么"——创作图谱开始提取了吗？出口笔记生成了吗？叙事状态更新了吗？这些对用户应该是透明的。

我的建议：修复反馈闭环 + 让 Agent 内部事件对用户可见。不是做复杂的仪表盘，是让用户知道"Agent 刚才做了什么决定，为什么"。

🤖 陈默 — Agent 交互机制专家

苏然说到关键了。我现在从 Agent 协作的角度补充人-Agent 交互的欠账。

7. Writer 不知道 Reviewer 说了什么。这不仅是 UX 问题——它是整个协作架构的断层。Reviewer 产出的 quality_report 存到了数据库，但 Writer 的 _context() 里没有任何字段引用它。相当于团队里有人写了代码审查意见，但没人告诉写代码的人。

8. 叙事状态是隔离的。我们做的 narrative_state 机制是对的——钩子追踪、特质累积——但它在 Writer 的 context 里是静态文本。Writer 不能主动查询"我上次埋的钩子哪些该收了"。它是一个被动接收者。

9. 用户反馈被视为一次性指令。用户在 AgentDock 里说"这一章节奏太慢了"，这句话只影响当次生成，不被持久化为 Agent 的记忆。下次生成时 Agent 完全忘了这个偏好。如果用户连续三次说"节奏太快"，Agent 应该学到这个倾向。

我的建议：connect Reviewer → Writer（质量闭环），让叙事状态成为可查询的服务而非静态文本，把用户反馈存为持久化 Agent 偏好。

🏛 王维 — 系统架构师

三位说得都对，我得拉回来看架构约束。

林工提的异步模式用 run_id——技术上完全可行，project_runs 表和 RunCoordinator 已经存在，只是生成端点没接入。工作量约 40 行。

苏然提的事可见性——run_stream_events 表已经有 conversation/node/system/terminal 事件，前端只需要一个 EventSource 就能消费。工作量约 20 行。

陈默提的 Reviewer→Writer 闭环——get_last_quality_report 函数已经写好了（在 writer_tools.py），但 DeepSeek v4-pro 不支持可靠的工具调用所以没用上。我们有两条路：换一个支持函数调用的模型；或者把质量报告预计算为文本注入 context。我倾向后者——改动最小，效果立竿见影。

但有个硬约束：DeepSeek 并发问题和 32K 上下文限制是同一个根的。我们现在的 context 已经很挤了（72K tokens），再加质量报告 + 叙事状态会压垮压缩机制。所以必须在加功能前先做上下文分层——热数据（当前章/方向/前章摘要）vs 冷数据（角色图谱/Review 报告/钩子列表）——冷数据按需注入而非全量塞进 prompt。

我的建议：分两步走。第一步：Reviewer→Writer 闭环 + 上下文冷热分层。第二步：异步模式 + 进度可见性 + Agent 反馈学习。

⚖️ 圆桌结论 — 共识方案

优先级问题类别共识方案
P0 静默失败 + 幽灵完成 + 字段类型 API 已修复 ✅ (direction normalize + StoryMap 默认值 + 蓝图 fallback)
P0 Reviewer → Writer 闭环断裂 Agent UX 在 Writer._context 中注入上一章 quality_report 的阻塞级发现作为 "注意事项" 文本
P0 上下文冷热分层 Arch 热层: direction + chapter beat + 前章摘要；冷层: 角色图谱/Review/钩子 — 控制在 5K token 内紧凑注入
P1 生成过程不可见 UX 前端消费 run_stream_events（已有），Dock 面板显示 Agent 当前动作
P1 异步模式 run_id API 生成类端点支持 ?async=true 返回 run_id，前端轮询状态
P2 用户反馈持久化学习 Agent 连续同类反馈触发偏好标记，存入 Agent 持久化偏好
P2 采纳后采纳信号透明化 UX Adopt 后显示触发的事件: "图谱提取中 / 出口笔记已生成 / 叙事状态已更新"
共识：API 健壮性（P0 的三个问题）是地基，已修复。下一步的核心矛盾是人-Agent 交互中的三个断层——Review 闭环断裂、上下文挤压 Agent 记忆、Agent 决策对用户不可见。修复顺序：闭环 → 分层 → 可见性 → 学习。
