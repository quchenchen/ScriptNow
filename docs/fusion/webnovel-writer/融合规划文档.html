🔧 第二档：需适配改造（Medium）

以下融合项需要改动 ScriptNow 核心架构或 AgentScope 框架，工期中等（1-3周/项），需技术评审后实施。

MD-1：合同驱动创作体系

Medium P0
webnovel-writer 做法ScriptNow 现状融合方案
三层合同树：
MASTER_SETTING.json → volume_{N}.json → chapter_{N}.json
+ chapter_{N}.review.json
唯一事实源，派生只读视图。
写入通过 accepted CHAPTER_COMMIT 驱动五维投影。 		StoryMap 已承担类似"蓝图"角色， 但缺乏严格的合同层概念和写前写后闸门。 审查结果独立存储，未与蓝图形成强约束链路。 改造 StoryMap 为合同驱动体系：
1. 定义三层合同：项目设定 → 卷/幕 → 章/场景，每层有 locked/append_only/override_allowed 策略
2. 写前生成章节合同（含 must_cover_nodes / forbidden_zones / chapter_directive）
3. 写后通过 accepted CHAPTER_COMMIT 驱动状态投影
4. 前端展示合同层状态（locked: N, append_only: M, overridable: K）
很高
预期收益
高
实施难度
2-3周
预估工期
关键改造点：webnovel-writer 的合同系统深度依赖 Claude Code 的文件系统和 subagent 机制。 ScriptNow 需要将其改造为 AgentScope 框架内的「合同管理 Agent + 合同 DB」， 同时保持 StoryMap 作为用户可编辑的蓝图视图。

5. 流水线编排器确保串行执行和失败隔离
很高

⚠️ 关键风险与缓解

风险影响缓解措施
AgentScope 框架限制 MD-2/3/5 的 Agent 流水线可能受限于 AgentScope 的多 Agent 编排能力 Phase 1 完成后做技术预研；必要时在 AgentScope 外实现编排层
合同系统过度工程化 MD-1 合同体系可能影响 ScriptNow 的灵活性和通用性 合同强度可配置（严格模式/建议模式/关闭）；保证 StoryMap 仍是用户可编辑的蓝图
上下文膨胀 三层记忆 + 合同注入可能导致 Agent 上下文过长 配合 QW-5 的分层加载策略；MD-3 实现严格的记忆预算管理
LLM 能力边界 五维审查 / Data Agent 的事实提取精度取决于 LLM 能力 审查 Agent 设计为"建议型"而非"裁决型"；关键决策保留人工确认
兼容性断裂 频繁架构变更可能导致已有项目数据不兼容 每个 Phase 提供数据迁移脚本；保持 API 版本化

core-constraints.md + genre-profiles.md + author_glossary.json + 37题材模板 + CSV多表检索
