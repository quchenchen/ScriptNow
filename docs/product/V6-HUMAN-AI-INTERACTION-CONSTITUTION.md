# ScriptFlow V6 人机协作交互宪法

> 状态：V6 人机交互设计的最高约束。页面、Agent 行为和 Skill 设计若与本文冲突，应修改实现或通过 ADR 说明覆盖理由。

## 1. 产品关系

ScriptFlow 不是用户向 AI 下单、等待成品的生成器，也不是要求用户管理多个机器人的项目管理器。它是一间持续理解作品的创作室：

- 用户掌握作品意图、审美判断和最终采用权。
- Agent Team 承担分析、准备、执行、校验和影响追踪。
- 系统承担状态、版本、来源、权限和恢复的确定性。

理想体验不是“AI 做得越多越好”，而是：用户把注意力留给有创作价值的判断，其余工作安静、可靠地推进。

## 2. 四组核心张力

| 张力 | 失败表现 | 设计答案 |
|---|---|---|
| 主动 / 打扰 | Agent 频繁弹窗、每一步都询问 | 按影响和可逆性决定是否打断 |
| 智能 / 越权 | AI 静默改变命题、人物或正文 | AI 默认只创建候选，不改变当前采用 |
| 复杂 / 清晰 | 工作台充满阶段、Agent 和状态 | 始终围绕当前作品对象组织界面 |
| 可控 / 流畅 | 所有动作都要比较和确认 | 低风险动作自动执行，高价值决策集中处理 |

## 3. 八条交互不变量

1. **作品先于 Agent**：界面主语是 Scene、Chapter、Character、Story Beat，不是“某 Agent 的聊天”。
2. **意图先于命令**：用户表达“想达到什么”，系统补全范围、依据与交付方式。
3. **候选先于覆盖**：AI 对创作内容的改变默认形成 Candidate Revision。
4. **证据先于建议**：审稿与改编建议必须指向正文、Story Core 或 Source Canon 证据。
5. **影响先于采用**：高影响修改在采用前说明会改变哪些对象。
6. **例外才打断**：可恢复的常规工作进入后台，方向冲突和不可逆风险才打断用户。
7. **状态不用猜**：用户始终能区分草稿、候选、当前采用、运行中和等待决定。
8. **失败可继续**：任何 Agent、保存或解析失败都不丢用户内容，并给出恢复路径。

## 4. AI 自主级别

每个 Task 根据“创作影响 × 可逆性 × 置信度”确定自主级别，不由 Agent 自己临时决定。

| 级别 | 定义 | 典型动作 | 用户体验 |
|---|---|---|---|
| A0 建议 | 只解释或提供选项 | 解释问题、列出三种方向 | 原位轻量呈现 |
| A1 准备 | 收集上下文、分析和排队 | 检索来源、检查连续性 | 后台执行，不打断 |
| A2 候选 | 生成可撤销内容 | 重写选区、生成 Scene | 创建 Revision，等待采用 |
| A3 受限执行 | 按已批准规则批量处理 | 格式规范化、已选范围改名 | 执行后摘要，可撤销 |
| A4 必须决策 | 改变方向或高影响事实 | 改人物动机、删除关键情节 | 进入 Decision Inbox |

禁止 A5“AI 自动采用高影响创作决定”。即使用户开启高自动化，也只能批量自动采用预先明确、可撤销且低影响的规则性修改。

### 自主级别判定

```text
是否改变当前采用内容？
├─ 否 → A0 / A1
└─ 是
   ├─ 是否纯规则、范围明确且一键可撤销？ → A3
   └─ 是否改变命题、人物、因果、来源取舍或多个下游？
      ├─ 是 → A4
      └─ 否 → A2
```

## 5. 人机交互的基本语法

每一次有效交互由六个要素构成：

```text
Intent（目标）
+ Object（对象）
+ Scope（范围）
+ Context（依据）
+ Constraint（约束）
→ Expected Delivery（期望交付）
```

用户不必每次填写六项。系统从当前选区、项目和历史决定中补全，并在执行前用一行可检查的 Task Brief 呈现：

> 写作者将基于 Story Beat 02 和林夏 Character v2，重写当前 2 句对白；保持信息量和场景节奏；交付一个候选 Revision。

若补全结果会改变任务性质，必须让用户修改 Brief；普通局部操作无需额外确认。

## 6. 三种用户输入方式

### 直接创作

用户亲自写、删、移动和修改正文。系统只负责保存、格式、引用和影响提醒，不把每次键入包装成 AI 任务。

### 对象化指令

用户先选择 Scene、段落、Character 或 Story Beat，再提出目标。对象和范围由选择建立，避免反复解释“你要改哪里”。

### 开放对话

用于模糊探索、反思和尚未形成对象的想法。对话中产生可执行意图时，Agent 必须转换为 Task Brief；不能让重要决定只停留在聊天记录。

三种方式可以互相转换，但直接创作永远是一级能力，不能强迫用户通过聊天编辑作品。

## 7. 注意力与打断规则

系统只有四种呈现强度：

| 强度 | 使用条件 | 表现 |
|---|---|---|
| Ambient | 保存、后台任务、无风险进度 | 状态文字或轻量图标 |
| Inline | 当前对象的局部建议或低风险问题 | 选区工具、行内标记、边注 |
| Inbox | 可延后但需要拍板 | Decision Inbox 聚合处理 |
| Interrupt | 数据丢失、权限、不可逆动作、当前操作无法继续 | 阻塞式对话框 |

不得因为 Agent Task 完成就弹出 Interrupt。完成结果进入 Delivery；只有用户当前正在等待该结果时，才用非阻塞提示邀请打开。

### Decision Budget

系统需要保护用户的决策精力：

- 同一原因影响多处时合并成一个 Decision，展示影响范围。
- 相似低风险 Revision 支持按规则批量处理。
- 每个 Decision 只问一个真正需要判断的问题。
- 默认推荐必须说明理由，但视觉上不能伪装成唯一正确答案。
- 已处理 Decision 可撤销，并保留当时证据。

## 8. 三种工作模式

### 专注创作

心智模型是“我在作品里”。正文占据主要空间，目录帮助定位，Agent 仅在选区、边注或可收起状态中出现。

进入条件：继续写作、打开正文、从 Story Map 选择 Manuscript Unit。

离开条件：用户主动查看结构，或打开需要比较的 Revision/Decision。系统不能因为审稿完成强制切走。

### 故事规划

心智模型是“我在理解和调整作品系统”。围绕当前对象显示来源、上游决定、同级关系与下游影响；不是永远展开的全局大图。

进入条件：查看 Character/Beat/伏笔、分析 dirty 影响、处理 Adaptation Map。

### 审阅决策

心智模型是“我在拍板”。同屏提供问题、证据、当前采用、候选方案、影响和明确动作。

进入条件：打开 Decision、Delivery 或 Revision compare。处理后返回原来的作品对象和滚动位置。

## 9. 六条关键交互闭环

### 9.1 继续创作

```text
Dashboard“继续创作”
→ 恢复上次 Manuscript Unit、光标/滚动位置与本地草稿
→ 展示一句下一步建议，但不遮挡正文
→ 用户写作或选区调用 AI
```

成功标准：用户进入项目后 5 秒内能继续输入正文，不必先理解 Agent 状态或项目阶段。

### 9.2 选区 AI 修改

```text
选择内容 → 选择目标/输入要求 → 系统补全 Task Brief
→ A2 后台生成 → 行内预览或 compare
→ 逐项采用 / 编辑后采用 / 保持当前
→ 记录 Revision 与 lineage
```

生成期间用户可以继续写其他位置。若原选区在生成期间被修改，Delivery 标为“基线已变化”，禁止直接采用，提供重新比较。

### 9.3 从模糊想法到故事决定

```text
开放对话 → Agent 澄清核心矛盾 → 形成 2–3 个差异化方向
→ 用户比较命题、人物代价和长期影响
→ 采用为 Story Core / 创建 Branch / 暂存
```

禁止用大量追问表单代替共同探索；也禁止 Agent 在一次长回复中同时确定命题、世界、人物和完整大纲。

### 9.4 审稿与修订

```text
Review Task → Issue（对象 + 证据 + 影响 + 建议）
→ 同因问题归组 → 生成候选 Revision
→ 用户处理 Decision → 重新检查受影响维度
```

分数只回答“整体趋势”，问题与证据回答“为什么”。忽略问题时允许记录理由，后续审稿不得无限重复提醒同一已接受风险。

### 9.5 改编取舍

```text
Source Canon → 解析与稳定引用 → Adaptation Map
→ 来源片段 / 改编决定 / 目标 Beat 三列对照
→ 用户处理关键删除、合并和原创新增
→ Scene 生成与来源审查
```

系统必须区分“忠实事实”和“创作策略”。事实冲突用 Alert；策略差异用 Decision，不能把某种改编观当成系统错误。

### 9.6 上游变化与 Cascade

```text
修改 Character / Beat / Story Core
→ 先预览影响 → 采用上游 Revision
→ 下游标记 Dirty，不自动重写
→ Agent 提出修复计划 → 用户选择范围
→ 批量生成候选 → 逐组采用
```

Dirty 表示“需要复核”，不是“内容错误”。用户可以确认下游仍然有效，系统记录判断并清除标记。

## 10. 状态与反馈细则

### 保存

`未保存 → 保存中 → 已保存` 使用 Ambient；失败时保留本地草稿并升级为 Inline。只有用户要离开且远端仍未保存时才 Interrupt。

### 生成

Task 必须显示具体动作、范围、负责人和可取消性。不要显示虚假百分比；能测量时显示“已检查 8/20 个 Scene”，不能测量时显示当前步骤。

### 候选

候选不能与当前采用使用相同视觉层级。紫色只表达 AI/分支身份，不表达优劣；采用状态使用绿色和明确文字。

### 错误

错误文案回答四件事：什么没有完成、什么已保留、为什么、用户现在能做什么。不得只出现“生成失败，请重试”。

## 11. 对话设计规则

- Agent 先回应当前对象和目标，再给建议。
- 单次最多提出一个阻塞性问题；非阻塞假设直接标明并继续。
- 建议不伪装成事实；来源事实附引用。
- 输出多个方案时必须有清晰差异维度，不生成同义改写。
- Agent 可以表达不确定性，并指出需要什么证据才能提高确定性。
- 用户说“就这样”“用第二个”等指代时，系统把它解析成明确 Decision 结果并回显对象。
- 对话摘要只保存已确认的偏好、决定和开放问题，不把所有聊天自动写入 Story Core。

## 12. 个性化与记忆边界

记忆分三层：

1. **作品事实**：Story Core 和 Source Canon，项目内最高优先级。
2. **项目偏好**：本项目的语言、节奏、禁用项和工作方式。
3. **个人偏好**：跨项目的界面与协作习惯。

Agent 从对话推断出的偏好先标记为“观察”，只有用户明确采用或多次稳定表现后才能建议保存。人物事实、剧情事实不得写入个人偏好。

## 13. 验收问题

每个功能上线前必须回答：

1. 当前主语是作品对象，还是 Agent/功能？
2. 用户的意图、范围和依据是否清楚？
3. 这是 A0–A4 中哪一级，为什么？
4. 结果会覆盖当前采用内容吗？
5. 用户在哪里看证据和影响？
6. 为什么现在需要打断用户？
7. 失败后哪些内容被保留，如何恢复？
8. 用户如何撤销、拒绝或纠正 AI？
9. 决定是否被结构化记录，而非只存在聊天里？
10. 处理完能否回到原作品位置继续创作？

任何无法回答其中两项以上的功能，不进入 UI 开发。
