# ScriptFlow V6 创作者中心纠偏方案

- **Status**: Proposed correction baseline
- **Date**: 2026-07-16
- **Supersedes in implementation**: 右栏中的抽象机制标签、占位式作品目录；永久约 1/3 协作区继续保留
- **Preserves**: Story Core、Revision、Candidate、Context Pack、连续性账本等后端能力

## 1. 结论

当前实现证明了数据可以从正文传入 Agent，再回写连续性账本，但没有证明创作者能够理解和控制这条链路。产品把系统内部对象暴露成了用户导航，把数据维护表单误当作专业创作能力。

V6 后续必须按创作者任务组织：定义作品目标与计划 → 建立故事圣经 → 规划作品目录 → 选择章/场并定义创作意图 → 写作与审稿 → 采用正文和事实变化 → 继续下一单元。

## 2. 当前问题

1. “连续性、指令、决策、节点、实体”是实现语言，不是创作任务。
2. “作品起点 + 第 N 章/场”不是 Story Map，不能规划、定位或管理完整作品。
3. 人物、组织、关系、世界和伏笔被压成右栏表单，没有形成故事圣经。
4. 创建流程漏掉产品契约规定的目标规模和创作方式。
5. Agent 虽读取 Context Pack，但没有向用户解释当前目标、输入事实、不变量、交付物和影响。
6. 永久约 1/3 右栏是用户明确确认的新产品决策；当前问题是右栏内容使用系统语言且与创作任务割裂，而不是右栏是否常驻。

## 3. 新的信息架构

| 空间 | 创作者的问题 | 核心对象 |
|---|---|---|
| 作品 | 我正在写哪一章/场？ | Story Map、正文编辑器 |
| 故事 | 作品的世界与长期结构是什么？ | Story Bible、人物、世界、关系、时间线、伏笔 |
| 审稿 | 哪些地方需要判断或修改？ | Review Issue、Revision、影响与证据 |
| 交付 | 是否达到交付要求？ | 范围、格式、检查、Export Job |

版本、来源和 Agent Activity 是上下文工具，不与上述创作空间争夺一级导航。

## 4. 项目创建与总体规划

创建项目收集或允许稍后补充：

- 创作来源与交付形态；
- 一句话命题或已有材料；
- 类型、受众、风格方向；
- 目标规模：卷数、章数、集数、单集场数、字数或时长；
- 创作方式：先完整规划、边写边规划、已有大纲导入；
- AI 自主级别和不可触碰边界。

创建后先形成可编辑的“项目计划候选”，用户调整并采用后再进入正文创作。

## 5. 真实 Story Map

左侧目录必须来自总体计划，而不是自动累加序号：

```text
小说：Volume → Chapter
剧本：Episode → Scene
```

每个单元显示标题、目标、状态、字数/时长、风险和待决策数量，并支持新建、重排、拆分、合并和修改目标规模。

## 6. 故事圣经

### 故事概览

Premise、主题、类型承诺、受众、视角、语气、结局方向和创作边界。

### 人物

- 稳定设定：身份、欲望、需求、恐惧、秘密、价值观、声音；
- 当前状态：位置、情绪、知识、目标、伤病和关系；
- 发展轨迹：变化发生在哪一章/场；
- 出场与弧光规划；
- 来源以及“用户设定 / Agent 候选 / 已采用事实”状态。

### 组织与关系

UI 不出现“实体”。只展示人物、组织、人物关系和阵营关系。关系记录双方、性质、当前状态、隐藏真相、变化历史与相关章节。

### 世界观

地点、时代、社会规则、权力结构、技术/魔法规则、禁忌、资源与代价。关键规则可冻结。

### 伏笔与故事承诺

区分伏笔、钩子、悬念和情节承诺，记录预设与实际埋入/强化/回收位置、正文证据、关联对象、紧迫度、历史和受影响单元。

## 7. 专注创作闭环

选择 Chapter/Scene 后，中央工作区依次呈现：

1. 本单元创作意图：目标、冲突、转折、情绪落点、必须保留、禁止改变。
2. 开始时连续性快照：人物状态、地点、时间、伏笔和上一单元出口。
3. 可直接编辑的正文。
4. 写作后提取的人物、关系、世界和伏笔变化候选。
5. 用户采用的正文与作品事实。
6. 明确传递到下一单元的状态。

## 8. Agent 如何参与

Agent 不是常驻聊天对象，而是围绕当前创作对象执行具名任务：

```text
选择 Chapter 3
→ 用户确认本章目标
→ 系统展示将使用的上下文
→ 写作者提交正文候选
→ 审稿人提交证据化问题
→ 用户直接编辑或采用 Revision
→ 系统提取作品事实候选
→ 用户采用事实
→ 更新故事圣经与 Chapter 4 上下文
```

每个 Task 显示执行者、目标、输入对象、不变量、交付物、预计影响和待用户决定事项。

### 设定变化传播契约

人物、组织、关系、世界规则或伏笔发生变化时，系统不能只把记录塞进 Context Pack。每次变化必须形成一个可解释的传播计划：

1. **变化是什么**：新增人物、关系转变、世界规则或伏笔计划。
2. **从哪里开始生效**：整体项目、指定 Episode/Chapter，或当前 Scene/段落。
3. **影响哪些内容**：当前候选、未来计划单元、已采用正文。
4. **如何处理**：仅供未来继承、修订当前单元、为既有正文创建 Cascade Revision、暂不处理。
5. **Agent 如何使用**：在 Task 开始前列出会读取的事实和本次必须体现的创作目标。
6. **结果证据**：交付后定位到正文片段，说明人物、关系或伏笔如何被体现。

默认规则：

- 修改故事圣经后，未来未生成单元自动读取最新已采用事实。
- 当前已有候选必须标记为 stale，用户决定重新生成或局部修订。
- 已采用正文绝不自动覆盖，只显示受影响单元并提供 Cascade Revision。
- “新增人物”必须进一步说明叙事功能、首次出场计划、人物声音和与现有人物的关系。
- “建立关系”必须说明客观关系、双方认知、当前状态、隐藏信息和计划变化点。
- “新增伏笔”必须说明埋入方式、预设位置、计划强化与回收位置；选择当前单元时必须创建正文 Revision，而不是只写账本。
- Agent 输出没有提供正文证据时，不能声称设定已经在创作中生效。

界面必须把传播结果写成创作者能理解的话，例如：

```text
二丫已加入故事圣经
计划首次出场：第 9 章
本章任务：以对手身份阻止主角取得值夜名单
将影响：第 9 章当前候选、第 10～12 章大纲
不会自动修改：第 1～8 章已采用正文
```

当前 demo runtime 若未消费人物、关系、世界和伏笔字段，界面必须明确标注“仅验证流程，不代表连续性生效”，不得用“已继承”误导用户。

## 9. 人的主观能动性

用户必须能直接编辑规划与正文、先写后分析、冻结核心规则、自定义章/场目标与审稿标准、要求多方案并组合、完全拒绝 AI、创建 Branch、纠正 Agent 上下文、区分母题重复与无意重复、手动调整目标规模与创作节奏。

专业能力体现在创作控制质量，不体现在 AI 按钮数量。

## 10. 右侧协作区

桌面端永久保留约 1/3 屏幕空间，持续呈现当前创作对象、连续创作状态和 Agent 协作；窄屏才降级为抽屉或底部面板。它不是独立聊天框，也不使用“连续性 / 指令 / 决策 / 节点”四个抽象标签，而围绕创作任务组织：

- **当前章/场**：目标、进度、人物与场景起始状态、需要推进的伏笔；
- **AI 协作**：当前 Agent、任务目标、正在读取的作品信息、交付状态；
- **等待我确认**：正文 Revision、人物/世界变化和结构影响；
- **传递到下一章/场**：采用后将延续的角色状态、场景出口、开放情节和伏笔。

完整人物、关系、世界和伏笔管理进入“故事”主工作区；右栏只显示与当前章/场直接相关的摘要和操作。版本血缘进入上下文工具。

## 11. 实施顺序

1. Project Plan 与目标规模。
2. Volume/Chapter、Episode/Scene 真实 Story Map。
3. 故事圣经主工作区，迁移右栏维护表单。
4. Chapter/Scene 创作意图与连续性快照。
5. 可解释 Agent Task、Delivery 与影响。
6. 审稿、Revision、Branch、Cascade 与交付闭环。

验收以创作者能独立完成并解释一次真实创作流程为准，不以表、API 或卡片数量为准。
